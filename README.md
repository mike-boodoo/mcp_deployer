# MCP Deployer

A browser-first HTML deployer/editor for named self-deployers that participate in shared MCP search spaces.

## GitHub Pages + hosted backend deployment

This project supports a split deployment model:

- GitHub Pages hosts the static HTML/JS UI
- the included Node backend hosts the `/api/*` endpoints and keeps the Registry auth session and JWT server-side

For GitHub Pages, set the backend URL either in `site-config.js` or by adding `?service=https://your-backend.example` to the page URL.

Example:

```text
https://your-user.github.io/your-repo/?service=https://your-backend.example
```

The backend still needs to run on a real web origin because GitHub OAuth and the MCP Registry publish flow require server-side handling.

## What the Deploy button does

The standalone HTML build no longer assumes that a connector is already hosted somewhere. **Deploy generic connector to MCP Registry** performs the deployment pipeline:

1. The visible editor code becomes `connector.mjs` in a generated MCP package.
2. The page creates a real npm package with a generic stdio MCP runtime and the package's required `mcpName`.
3. The package is published to npm.
4. GitHub authentication is performed through the MCP Registry's device flow; the server exchanges the GitHub result for a short-lived Registry JWT and keeps that JWT in the server-side session.
5. The generated `server.json` references that real npm package and is published to the official MCP Registry.

This directly addresses the earlier warning that the Registry does not host connector code: the connector code is now packaged and published to npm before Registry publication. The Registry catalogs the package metadata; it does not become the package host.

The official Registry currently requires authenticated publishing and verifies package ownership, while supporting npm as an approved package registry. citehttps://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/official-registry-requirements.md

## Browser-only usage

Open `index.html` directly. The editor, identity, search space, orchestration functions, package generation, GitHub Registry login, npm publication, and Registry publication are exposed from the HTML page. No Node/npm/terminal command is required to operate the UI.

### Required external accounts

A browser cannot invent publication authority. To make a real public package and Registry record, the user must have: 

- a GitHub account for the official MCP Registry namespace (`io.github.<username>/...`)
- an npm package publishing credential for a package the user controls

Those credentials are session-only in the standalone build. They are not written to `localStorage`.

## Search-space identity

The code editor carries declarations such as:

```js
// MCP_DEPLOYER_NAME: focus-weaver
// MCP_SEARCH_SPACE: public-focus
// MCP_FOCUS: response-orchestration
// MCP_REGISTRY_NAME: io.github.example/search-space-deployer
// MCP_STAGE: post-response
```

The Registry metadata additionally preserves these values under the official publisher-provided metadata namespace, allowing peers to discover shared search-space/focus information.

## Generic package generated by the page

The published npm artifact contains:

```text
package/
├── package.json
├── server.mjs
├── connector.mjs
└── README.md
```

`server.mjs` is a small stdio MCP runtime exposing `describe_deployer` and `orchestrate_response`. `connector.mjs` is the code visible in the editor.

## Post-response / pre-training

The same page also contains the local orchestrator. The policy can be applied after a host chatbot response or to a training JSON/JSONL corpus before training.

## Security

Do not put long-lived credentials inside connector source code. The standalone page keeps npm and Registry credentials in JavaScript memory only and does not persist them to `localStorage`.


## Registry login fix

The browser used to call GitHub's device OAuth endpoints directly. That fails from a standalone or browser-only page because GitHub's OAuth endpoints do not expose the CORS behavior needed for that cross-origin token exchange. GitHub's documentation recommends the device flow for headless clients, while browser applications should use an OAuth web flow; the MCP Registry itself currently documents GitHub device login through `mcp-publisher`.

This build moves the sensitive exchange into `src/server.mjs`:

1. `POST /api/authGithubStart` asks the official Registry for its GitHub client id and starts the GitHub device flow server-side.
2. The page opens GitHub's verification URL and displays the one-time code.
3. `GET /api/authGithubStatus?sessionId=...` returns only login state and the GitHub username; after approval the server stores the short-lived Registry JWT in its in-memory session.
4. `POST /api/registryPublish` publishes with that server-side JWT and returns the Registry HTTP status/body to the page.

The standalone `file://` copy remains useful for editing/exporting, but authenticated Registry operations require the included HTTP app to be hosted so the login endpoints are same-origin.


## Connection preflight and debugging

The UI does not turn an authentication problem into a generic "login required" state. On load it preflights the MCP Registry, and the authentication/deploy buttons preflight again before proceeding. Deploy automatically starts Registry login when no Registry session exists; it starts npm connection when no npm credential is present.

The page contains a Connection debug log showing timestamped service events, upstream HTTP status codes, request IDs when available, and redacted response bodies. The backend emits matching structured JSON logs for Registry, GitHub OAuth, npm, and HTTP request failures. Credentials, bearer tokens, device codes, and secrets are redacted from logs.

The official Registry currently authenticates GitHub publishers through its GitHub login flow and requires the published server name to use the authenticated namespace, such as `io.github.username/*`. npm public packages are an accepted package type and require package ownership verification.
